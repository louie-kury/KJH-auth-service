# 인증 서비스 요구사항

Auth Service는 로그인 정보를, User Service는 자체 프로필을 관리한다. 두 프로필 모델의 관계는 [아키텍처](architecture.md)를 참고한다. 수의사 회원가입은 수의사 서비스가 담당한다.

| ID | 기능 | 요구사항 |
| --- | --- | --- |
| AUTH-001 | 로그인 | 아이디와 비밀번호로 로그인하고 성공하면 JWT를 발급한다. 아이디 미존재와 비밀번호 불일치에는 같은 실패 응답을 반환한다. 화면 문구 예시는 “아이디 또는 비밀번호를 확인해 주세요.”다. |
| AUTH-002 | 인증 검증 | Gateway는 유효한 JWT에서 사용자 ID를 추출해 대상 서비스에 전달한다. 대상 서비스는 그 ID로 요청 주체를 식별하고 접근 권한을 판단한다. JWT가 누락·만료·위조된 보호 요청은 거부한다. |
| AUTH-003 | 세션 갱신 | 유효한 Refresh Token으로 세션을 갱신한다. Rotation 적용 여부는 팀 논의 후 정한다. |
| AUTH-004 | 로그아웃 | 현재 세션을 로그아웃한다. 기존 토큰의 즉시 무효화 여부는 팀 논의 후 정한다. |
| AUTH-005 | 보호자 회원가입 | 로그인 아이디는 사용자가 직접 입력한다. 아이디, 이름, 닉네임, 비밀번호, 전화번호, 성별, 생일, 주소, 약관 동의, 이메일은 필수다. 닉네임은 2~10자다. 이메일 인증을 완료해야 가입할 수 있다. 가입 시 CAREGIVER를 자동 부여한다. 서버는 최종 저장에서 아이디·닉네임·이메일의 유일성을 보장한다. |
| AUTH-006 | 이메일 인증 | 보호자 가입용 인증번호를 이메일로 발송하고 검증한다. 검증 성공 시 인증한 이메일에 묶인 만료 가능한 일회용 가입 증명값을 발급한다. |
| AUTH-007 | 비밀번호 재설정 | 이메일로 본인 확인을 마친 뒤 새 비밀번호를 설정한다. 재설정 성공 후 기존 세션의 처리 방식은 팀 논의 후 정한다. |
| AUTH-008 | 소셜 로그인 | 네이버와 카카오를 지원한다. 이미 가입된 이메일이면 기존 계정이 있음을 안내한 뒤 로그인 페이지로 이동한다. 신규 소셜 계정에는 2~10자의 닉네임을 무작위로 부여하고 이후 변경할 수 있게 한다. |
| AUTH-009 | 아이디 찾기 | 가입 이메일로 아이디를 찾는다. 본인 확인과 결과 안내 방식은 미결정이다. |
| AUTH-010 | 비밀번호 찾기 | 이메일로 본인 확인을 하고 비밀번호 재설정(AUTH-007)으로 이어진다. |
| AUTH-011 | 회원 탈퇴 | 탈퇴 즉시 새 로그인을 차단한다. 기존 세션의 즉시 종료 여부는 팀 논의 후 정한다. 같은 이메일로 재가입할 수 없다. 같은 아이디의 재사용 여부는 탈퇴 기능 설계 시 정한다. |
| AUTH-012 | 아이디 중복 확인 | 가입 화면에서 아이디의 현재 사용 가능 여부를 확인한다. |
| AUTH-014 | 닉네임 중복 확인 | 가입 화면에서 닉네임의 현재 사용 가능 여부를 확인한다. |

## 보호자 가입 완료 기준

- 프런트엔드는 현재 입력한 아이디와 닉네임이 각각 중복 확인을 통과하고 이메일 인증이 완료된 경우에 가입 제출을 허용한다. 아이디나 닉네임을 변경하면 해당 항목을 다시 확인한다. 이메일을 변경하면 변경한 주소로 다시 인증한다.
- 가입 요청에는 이메일 인증 증명값을 제출한다. 서버는 중복 확인 버튼의 사용 여부에 대한 증명은 요구하지 않으며, 최종 저장에서 중복을 거부한다. 서로 충돌하는 동시 가입은 DB에서 먼저 저장을 확정한 한 요청만 성공한다.
- `svc_identity`의 계정·자격 증명·프로필을 하나의 트랜잭션으로 저장하고 커밋 후 가입 성공을 반환한다. User Service의 프로필 생성은 별도 트랜잭션이다.
- 이메일의 유일성은 최종 가입에서 검증한다. 기존 이메일 중복 확인 요구사항(AUTH-013)은 제외한다.

## 미결정 사항

- 가입 후 User Service 프로필 생성의 연동 방식과 실패·재시도 정책, 두 서비스에 걸친 탈퇴 처리 순서와 부분 실패 시 동작을 정한다. 탈퇴 본인 확인과 서비스별 삭제·보존 및 세션 수 제한 기준도 정한다.
- 등록된 소셜 연결로 다시 로그인하는 경우와 소셜 연결 없이 가입 이메일만 일치하는 경우의 처리 기준을 확인한다. 공급자의 이메일이 없거나 신뢰 여부를 확인할 수 없는 경우도 정한다.
- 호출자와 신뢰 경계는 [아키텍처](architecture.md), 응답과 오류는 [API 계약](api.md), 자격 증명과 세션은 [보안](security.md)을 참고한다.
