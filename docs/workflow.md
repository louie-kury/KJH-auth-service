# 개발 워크플로

작업 시작 시 [작업별 문서](../AGENTS.md#작업별-문서)에서 관련 항목을 확인한다. 문서 수정이나 리뷰처럼 범위가 제한된 요청에는 필요한 단계만 적용한다.

## 작업 단위

- 이슈 하나에 대화 하나와 작업 브랜치 하나를 사용한다. 같은 이슈의 결정 사항과 리뷰 후속 작업은 해당 대화에서 이어간다.
- 새 작업은 관련 지침과 현황을 확인한 뒤 이슈 단위로 나누고, 해당 이슈의 목적·범위·완료 기준·예상 커밋 단위와 결정이 필요한 사항을 사용자에게 설명한다.
- 커밋은 독립적으로 검토하거나 되돌릴 수 있는 변경 단위로 나눈다. 동작 변경과 해당 동작을 검증하는 테스트는 같은 커밋에 담는다.
- 각 커밋 단위의 작업과 검증이 끝나면 완료 내용과 결과, 전체 계획상 현재 위치, 다음 단계를 사용자에게 알린다. 계획이 바뀌면 변경 이유와 영향을 함께 설명한다.
- 커밋마다 대상 변경과 메시지, 검증 결과를 제시하고 사용자의 명시적 승인을 받은 뒤 실행한다. 승인받기 전에는 커밋하지 않는다. 사용자가 특정 단계에서 기다리라고 한 경우 해당 단계에서 멈춘다.
- PR에는 이슈의 완료 기준을 충족하는 커밋과 검증 결과를 담는다.

## GitHub 작업 순서

1. **이슈 생성** — 작업 목적, 범위와 완료 조건을 기록한다.
2. **기준 브랜치 최신화** — 로컬 `dev`를 원격 `dev`의 최신 상태와 동기화한다.
3. **작업 브랜치 생성** — 최신 `dev`에서 작업 브랜치를 만든다. 이름은 [Git 컨벤션](conventions.md#git)을 따른다.
4. **작업 진행** — 합의한 범위의 기능과 필요한 테스트를 작성한다. 담당자 배정은 아래 역할과 단계별 통과 기준을 따른다.
5. **로컬 검증** — 변경에 필요한 빌드·테스트를 실행한다. Lint와 아키텍처 규칙 검사는 프로젝트에 구성된 경우 실행한다. [로컬 검증 명령](#로컬-검증)과 [테스트 범위](testing.md)를 참고하고, 실행하지 못한 항목과 이유를 기록한다.
6. **커밋** — 대상·메시지·검증 결과를 보고하고 사용자 승인을 받은 뒤 [Git 컨벤션](conventions.md#git)에 따라 실행한다.
7. **푸시** — 작업 브랜치를 원격 저장소에 반영한다.
8. **PR 생성** — `dev`를 대상으로 PR을 만들고 변경 사항과 검증 결과를 설명한다. 제목과 작업 이슈 연결은 [Git 컨벤션](conventions.md#git)을 따른다.
9. **CI 검증 및 코드 리뷰** — 자동 검사 결과를 확인하고 변경 내용을 리뷰한다.
10. **리뷰 반영 및 승인** — 리뷰 의견을 반영하고 변경 범위를 재검증한다. 수정한 PR에 필요한 최종 승인을 받는다.
11. **머지** — `dev`에 적용되는 GitHub Ruleset과 브랜치 보호 규칙의 필수 검사·승인 조건을 충족한 뒤 사람이 병합한다. [GitHub Ruleset 규칙](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
12. **이슈 종료 확인 및 작업 브랜치 삭제** — [PR과 이슈 완료 확인](conventions.md#pr과-이슈-완료-확인)에 따라 머지와 이슈 종료 상태를 각각 확인한다. 작업 브랜치는 머지 완료를 확인한 뒤 삭제한다.
13. **로컬 기준 브랜치 최신화** — 로컬 `dev`로 돌아가 최신 상태를 동기화한다.

## 로컬 검증

JDK 17 환경에서 저장소 루트의 Gradle Wrapper로 실행한다. 기본 테스트는 데이터베이스 연결 없이 Spring 애플리케이션 컨텍스트가 시작되는지 확인한다.

| 검증 | Windows PowerShell | macOS·Linux |
| --- | --- | --- |
| 컴파일, 패키징, 테스트 | `.\gradlew.bat clean build` | `sh ./gradlew clean build` |
| 테스트 | `.\gradlew.bat test` | `sh ./gradlew test` |

## 역할과 단계별 통과 기준

메인은 현재 사용자 대화 세션이다. 프로젝트 에이전트는 네 담당자만 등록한다. 메인은 호출할 때 담당자에게 작업 목표, 수정 허용 경로, 기대 결과와 검증 범위를 전달한다.

| 담당 | 하는 일 | 수정할 수 있는 것 |
| --- | --- | --- |
| 메인 오케스트레이터 | 사용자 대화, 작업과 범위 배정, 결과 확인, 단계 통과·재작업 판단 | 사용자가 허용한 설정·통합 작업. 다른 담당에게 배정한 작업은 해당 담당에게 돌려보낸다. |
| planner | 초기 설계, 최종 문서 동기화 | 메인이 지정한 설계·API·안내 문서 |
| implementer | 합의한 설계 구현과 버그 수정 | 실제 구현 코드와 허용된 구현 설정 |
| tester | 기대 결과를 기준으로 테스트 작성·실행 | 테스트 코드, 테스트 전용 fixture, 허용된 테스트 설정 |
| reviewer | 코드 리뷰 또는 별도 호출의 블랙박스 QA | 읽기와 안전한 검증 실행, 결과 보고 |

### 작업 순서와 통과 기준

1. **설계** — planner가 변경 범위, 관련 요구사항, 관찰 가능한 기대 결과를 제시한다. 메인은 배정 범위의 기대 결과와 사전 승인 충족 여부를 확인한다. 미결정 정책이 구현이나 테스트 결과에 영향을 주면 해당 범위는 정책 결정 후 배정한다. 독립적인 범위는 먼저 배정할 수 있다.
2. **구현** — implementer가 합의된 설계를 구현한다. 메인은 구현 결과와 변경 파일이 배정 범위에 맞는지 확인한다.
3. **테스트** — tester가 기대 결과에 맞는 테스트를 작성하고 실행한다. 메인은 변경 범위와 결과를 확인한다. 실패하면 구현 결함은 implementer에게, 합의와 다른 테스트는 tester에게 돌려보낸다. 기대 결과가 불명확하면 먼저 정책을 확인한다. 수정 후 관련 테스트를 다시 실행한다.
4. **리뷰** — reviewer가 변경과 연관 코드의 결함 및 회귀 위험을 검토한다. 블랙박스 QA가 필요하면 공개 인터페이스와 기대 결과를 지정해 별도 호출한다. 메인은 통과를 막는 발견 사항을 해당 담당자에게 돌려보내고 재검증 결과를 확인한다.
5. **문서 동기화** — planner가 승인된 최종 동작과 지정 문서를 대조해 필요한 내용을 갱신한다. 메인은 문서와 검증 결과를 확인하고 사용자에게 보고한다.

   메인은 모듈 경계, 데이터 저장 방식, 외부 연동 등 이후 작업에 영향을 주는 승인된 설계 결정 중 기록할 항목을 지정한다. planner는 결정의 배경, 검토한 대안, 선택 이유, 영향을 `docs/adr/`에 기록한다. 첫 ADR을 작성할 때 디렉터리를 만든다.

담당별 변경 파일은 작업 전 상태와 배정 경로를 기준으로 대조한다. 범위를 벗어난 변경이나 실행하지 못한 검증이 있으면 메인이 영향을 확인한 뒤 다음 단계 진행 여부를 판단한다. 구현·테스트의 경로 제한은 에이전트 지침으로 적용한다.
