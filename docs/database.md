# 인증 서비스 데이터 설계 초안

MySQL 8.4.13을 사용한다. Auth Service는 로그인 정보를 관리하고 User Service는 프로필을 관리한다. [svc_identity ERD](erd.md)를 스키마 기준으로 삼는다. 두 서비스 간 사용자 ID 연결 방식은 미결정이다.

| 데이터 후보               | 설계 시 확인할 사항                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 사용자 식별자와 계정 상태 | Auth Service가 로그인 아이디와 가입 이메일을 관리한다. 프로필과 연결할 ID, 계정 상태의 소유권과 변경 반영 시점을 정한다.      |
| 자격 증명 검증 정보       | Argon2id 해시와 비밀번호별 무작위 Salt를 사용한다. 저장 형식과 삭제 기준은 정해야 한다.                                       |
| 세션 상태                 | 서버가 상태를 관리하는 경우 만료·폐기·갱신 상태와 중복 요청 처리                                                              |
| 이메일 인증 및 요청 제한  | 인증번호 HMAC, 발급 상태와 요청 제한을 Redis에서 관리한다. 가입 증명 해시는 Redis 키에 사용하고 이메일·목적을 TTL 10분으로 저장한다. |
| 감사 이벤트               | 기록 목적, 최소 필드, 접근 권한, 보존 및 삭제 기준                                                                            |

## 데이터 제약

- 공개 식별자는 하이픈을 포함한 36자 UUID 문자열이다. JWT에서 어떤 사용자 ID를 전달할지는 [아키텍처](architecture.md)의 팀 논의 항목을 따른다.
- 공통 사용자 유형 값은 `CAREGIVER`, `VETERINARIAN`이다. 보호자 가입 시 `CAREGIVER`를 부여한다.
- 계정 상태 값은 `PENDING`, `ACTIVE`, `WITHDRAWN`, `SUSPENDED`다. 성별 값은 `MALE`, `FEMALE`, `UNKNOWN`이다.
- svc_identity.account의 이메일 고유 제약을 적용한다. 탈퇴한 계정의 이메일은 재가입에 사용할 수 없다. 탈퇴 후 아이디 재사용 허용 여부는 미결정이다.

## ERD 테이블과 적용 범위

- svc_identity의 user_profile은 닉네임과 사용자 유형을 저장한다. User Service의 프로필은 별도 모델이다.
- outbox는 Kafka에 발행할 이벤트를 기록한다. 이벤트 계약과 발행·재시도 방식은 연동 설계에서 정한다.
- 관리자 테이블 admin_account와 admin_login은 ERD에 포함되어 있다. 인증 서비스에서 구현할 범위는 팀 논의 후 정한다.
- 세션과 토큰 저장 방식은 Rotation 및 즉시 무효화 정책이 정해진 뒤 결정한다.

## 가입 이메일 인증 저장 경계 (AUTH-006)

- 발송 예약과 발송 한도 반영, 코드 활성화와 이전 코드 폐기, 코드 비교와 시도 횟수 갱신 또는 성공 시 소비를 각각 Redis의 원자적 작업으로 처리한다. 유효기간과 한도는 [보안 정책](security.md#보호자-가입용-이메일-인증)을 따른다.
- 스크립트가 코드와 이메일·IP·서비스 전체 제한 키를 함께 갱신할 수 있도록 AUTH-006의 Redis 쓰기는 단일 주 노드에서 처리한다.
- 가입 증명값은 `auth:{signup-email}:proof:<SHA-256 hex>` 키에 저장한다. 값은 `CAREGIVER_SIGNUP`과 정규화 이메일을 줄바꿈으로 구분한 문자열이다. SET과 TTL 10분을 한 명령으로 적용하며 원본 증명값은 저장하지 않는다.
- Redis에서 해당 코드를 소비한 요청만 증명 해시를 키로 저장한다. 저장 실패 시 코드는 소비된 상태로 유지하며 재인증한다.
- 가입 증명값은 TTL 만료로 자동 삭제된다. Redis 유실 또는 소비 후 가입 저장 실패 시 재인증한다.

## 보호자 가입 트랜잭션 (AUTH-005)

- `svc_identity`의 `account`, `login_credential`, `user_profile`을 하나의 MySQL 트랜잭션으로 저장한다. 커밋 완료가 가입 성공 기준이며 User Service의 프로필 저장은 별도 트랜잭션이다.
- 최종 가입은 `account.email`, `login_credential.login_id`, `user_profile.nickname`의 고유 제약으로 보호한다. 사전 중복 확인 결과와 관계없이 저장 시 충돌한 요청은 중복 오류로 처리한다.
- 후속 AUTH-005는 입력 검증 후 Redis에서 증명 해시·이메일·목적·만료를 확인하고 원자적으로 소비한다. 소비 후 MySQL 가입 저장이 실패하면 재인증한다. 가입 후 User Service 연동 방식은 별도로 정한다.

## 저장 방식 확정에 필요한 결정

- 승인된 기능과 실패 시 기대 결과를 기준으로 유일성 제약, 조회 조건, 트랜잭션 경계를 정한다. 갱신과 폐기가 같은 세션에 동시에 요청될 때의 결과는 서비스 정책과 맞춘다.
- 스키마를 정하면 마이그레이션 적용 순서, 배포 중 호환성, 실패 시 복구 절차를 기록한다.
- 민감 데이터 처리 기준은 [보안](security.md), 검증 범위는 [테스트](testing.md)를 따른다.

## Flyway 운영

향후 MySQL 스키마 변경은 Flyway로 관리한다. AUTH-006은 Redis만 사용하므로 적용할 마이그레이션이 없고 현재 Flyway 실행은 비활성화한다. 실제 MySQL 변경을 도입할 때 기존 스키마와 권한을 확인한 뒤 활성화한다.
